# Retrieval Evaluation Methodology

Historical Phase 3 and Phase 4 retrieval evaluation protocol. See [Pipeline Evaluation & Benchmark Report](evaluation_report.md) before using these outputs for a new comparison. The 18 reviewed questions are development cases; known-source hit and MRR are diagnostics, while corpus-wide recall needs complete relevant-paper judgments. The ten-chunk protocol pads missing paper ranks as misses; the document-pool protocol marks them unavailable. The reproducibility manifest's recorded reviewed-dataset digest must be rechecked against the actual checked-in file before rerunning.

From the repository root:

    python evaluator.py --audit-only
    python evaluator.py --dataset reviewed_dataset.json --index-tag "fixed-index-v1"
    python evaluator.py --dataset reviewed_dataset.json --limit 10 --index-tag "fixed-index-v1"

The default processes every eligible answerable record; the explicit limit caps attempts and appears in output. Audit mode needs only the Python standard library. Retrieval mode needs the existing Chroma vault, backend dependencies, and BGE embedding model, but no external LLM API key, remote provider, or reranker model. The checked-in 18 candidates have zero eligible records, so default output contains gaps but no scores. A run with eligible records requires a non-placeholder `--index-tag`; choose a stable identifier for the frozen local vault and record how it was made. A tag alone does not prove that the vault is unchanged. The evaluator hashes backend settings and records the hash alongside the dataset hash and code commit; it does not fingerprint model weights or vector contents. Report files in ignored evaluation_results/ are annotation-gaps.csv, per-question.jsonl, aggregate.json, and report.md. The default API button audits the checked-in candidates; use the CLI with a reviewed dataset and index tag for a scored run.

The unit is a canonical indexed source filename, not a mutable chunk ID. The evaluator asks `search_vault` for ten candidate chunks and considers only the first ten returned chunks, which may include repeats from one paper. Paper ranks are first occurrences of filenames within that fixed chunk window; the report records both chunk and distinct-paper counts. P@10 is therefore **not** a claim that the system searched until it found ten unique papers. Raw ranked child chunk IDs and converted one-based PDF pages are retained for inspection. Hybrid retrieval returns expanded parent text and metadata, but does not expose its fused ranking scores; per-rank score is null. This measures hybrid retrieval before CRAG reranking, grading, correction, fallback, and generation.

At K=1,3,5,10, P@K is distinct relevant retrieved papers divided by K. Missing ranks count as non-relevant. R@K divides by distinct verified relevant papers. Hit@K is 1 for a hit, else 0. MRR is inverse first relevant rank, else 0. Graded NDCG uses (2^grade - 1)/log2(rank + 1), divided by the ideal ranking of verified grades. Duplicate chunk hits cannot inflate document counts. Means are macro averages, with a count per metric.

Unjudged retrieved papers are not assumed irrelevant. By default only verified relevant papers count as judged; P@K and NDCG@K are omitted at a cutoff if any retrieved paper in its prefix lacks a positive evidence label or an explicit judged_nonrelevant_papers label. Missing ranks still count as non-relevant. Report each metric's contributing query count because these omissions can bias a partial macro mean. Recall, hit, and MRR assume annotators found all relevant papers in the fixed corpus; incomplete annotation can bias them. Failed queries are counted separately and excluded from means; `retrieval_failed` and `partial_results` distinguish runtime failures from missing labels. Verified unanswerable questions have no retrieval denominator and are listed separately. No true negatives, accuracy, specificity, or TN-derived F1 are reported. Pilot scores from a handful of annotated records are not a stable held-out benchmark.

Answer correctness needs a human-approved reference and required-claim rubric. Reference answers and claim tables are drafted with AI assistance, then personally checked by the human reviewer against cited physical research papers and approved. Human verification certifies support in the cited passage; it does not establish that every other corpus paper is nonrelevant. Faithfulness checks factual claims against the context actually passed to generation. Citation correctness checks each claim's cited paper and one-based page. Abstention requires human confirmation that the fixed full corpus lacks an answer. These four assessments are distinct from retrieval and are measured in the end-to-end evaluation pipeline (`scripts/run_real_pipeline_evaluation.py`) using OpenRouter (`meta-llama/llama-3.3-70b-instruct`). Results are audited with human verdict forms and preserved in [`docs/evaluation/evaluation_report.md`](evaluation_report.md).
